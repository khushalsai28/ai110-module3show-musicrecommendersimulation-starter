# Music Recommender Simulation

## Project Summary

This CLI-first classroom simulation turns a small song dataset and a listener's taste profile into an explainable, ranked list. It uses content-based matching: it compares each song's genre, mood, energy, and optional acousticness to the listener's preferences. It does not learn from real listening histories or predict real-world popularity.

## How The System Works

Real streaming services can combine **collaborative filtering** (patterns in what many listeners play, like, skip, or add to playlists) with **content-based filtering** (similarities in song features such as genre, tempo, or mood). A listener's taste can be represented by these interaction signals, explicit preferences, and inferred patterns. This project implements only a transparent content-based baseline; its small hand-authored dataset is not a model of Spotify or TikTok's proprietary systems.

### Data flow

`Taste profile -> score each song -> sort by score -> return top K with reasons`

- Each `Song` has an ID, title, artist, genre, mood, energy, tempo, valence, danceability, and acousticness.
- A `UserProfile` stores favorite genre and mood, target energy, and whether the listener likes acoustic music.
- The dictionary-based CLI accepts genre, mood, energy, and optionally `likes_acoustic`.
- Each song receives **+2.0** for a genre match and **+1.0** for a mood match. Energy adds `max(0, 1 - abs(song energy - target energy))`, so a closer value earns more points. When `likes_acoustic` is supplied, acousticness contributes up to **+0.5** for matching the preference.
- `score_song` evaluates one song and returns its numeric score plus reasons. `recommend_songs` applies that scoring rule to every song, sorts scores from highest to lowest (preserving input order for ties), then returns at most K results. Ranking is a separate step from judging an individual song.
- Tempo, valence, and danceability are loaded into the song records but are not used in the current score.

### Dataset and known biases

The CSV contains 16 fictional songs across 13 genre labels and 11 mood labels. Genres and moods are unevenly represented: for example, there are three lofi songs and two pop songs, while most genres have one. A feature-driven system can repeatedly surface songs matching its strongest weighted features, and a narrow catalog can make those patterns look like user preferences. The recommender has no artist/genre diversity rule, listening history, popularity signal, lyrics, or user feedback.

## Getting Started

Run these commands from the repository root:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m src.main
```

The core recommender uses Python's standard library. The repository also lists pytest, pandas, and Streamlit for optional exercises and tooling.

### Running Tests

```powershell
python -m pytest -q
```

## Experiments and Evaluation

The CLI compares high-energy pop, chill acoustic, intense metal, and a conflicting metal/calm/high-energy profile. The preferred-genre song rises for the pop and metal profiles; the chill profile instead favors lofi songs with close energy and acousticness. The conflicting profile shows the weakness of independent feature scoring: it ranks a high-energy metal song first even though that song does not match the requested calm mood.

As a weight-shift experiment, genre weight was halved from 2.0 to 1.0 while energy similarity was doubled. The top five remained the same songs, but Rooftop Lights moved above Gym Hero because its energy was closer to the target. This changes ordering without proving which list is better: there is no user feedback or **ground truth** preference label in this toy dataset. The tests check expected scoring, ranking, explanations, input immutability, and CSV numeric conversion; they are not a real-world recommendation-quality evaluation.

## Limitations and Risks

- The dataset is small, fictional, and imbalanced, so it cannot represent the breadth of music or listeners.
- The fixed weights encode design choices and can introduce **bias** toward a matching genre or mood even when another feature better captures a listener's intent.
- Similarity uses only basic metadata and does not model context, culture, lyrics, new releases, or evolving preferences.
- Without diversity constraints, recommendations can become repetitive; no interactions or ground truth are available to measure satisfaction.

## Reflection

This simulation makes the transformation from input features and user preferences to a score and ranked prediction visible. The weight experiment demonstrates that a ranking algorithm can change recommendations even when its dataset and listener profile stay fixed. Real systems need broader evaluation and feedback, while a simple content-based model can make its reasoning clear but may reinforce a filter bubble if the catalog and features are narrow.
